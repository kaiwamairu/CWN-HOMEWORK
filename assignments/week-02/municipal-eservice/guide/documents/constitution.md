# เทศบาลนครตัวอย่าง e-Service Constitution

## Core Principles

### I. รักษาโจทย์และที่มาของกฎ

ทุกเอกสารและงานพัฒนาต้องรักษา `brief/BRIEF.md`, `USER-STORIES.md`, `REQUIREMENTS.md`,
`CONTRACT.md`, `TEST-DATA.md`, `TEST-PLAN.md`, `BUGS.md` และ `DECISIONS.md` ไว้ครบถ้วน
ห้ามแก้ตัวเลข seed ข้อความที่ต้องตรง หรือผลคาดหวังเพื่อให้ระบบผ่านการทดสอบ
เมื่อแหล่งข้อมูลขัดกัน ให้ใช้ `DECISIONS.md` และให้ §18 ชนะข้อก่อนหน้า ตามคำสั่งในไฟล์นั้น
ต้องบันทึกการตีความพร้อมแหล่งอ้างอิง กฎ [D], [R], A-01–A-63 และคำถาม Q-01–Q-36
ต้องคงป้ายที่มา สมมติฐานสำหรับห้องเรียนไม่ใช่คำตอบที่หน่วยงานจริงยืนยันแล้ว

### II. สัญญาที่ตรวจสอบได้จากภายนอก

ต้องทำตาม `CONTRACT.md` ทุกส่วน: เส้นทางหน้าและ API, บทบาท, HTTP status, JSON,
`data-testid`, `data-*`, ข้อความไทย, วันที่ เงิน และไฟล์ส่งออก
ปุ่มที่ต้องไม่มีต้องไม่ render; ปุ่มที่ใช้ไม่ได้ต้อง disabled
การปฏิเสธต้องตรวจที่เซิร์ฟเวอร์ด้วย ห้ามถือว่าการซ่อนปุ่มเป็นการควบคุมสิทธิ์
เอกสารออกแบบต้องชี้ว่าทุกความสามารถและทุกกฎตรวจด้วย TC ใด หรือการตรวจเสริม
แบบ unit/inspection ใด โดยไม่เพิ่มรหัสในชุด 51 TC เดิม เป้าหมาย production
ที่ห้องเรียนพิสูจน์ไม่ได้ต้องมีวิธีตรวจที่เสนอและคงเป็น open item ตามต้นฉบับ

### III. เวลาและการเปลี่ยนสถานะต้องให้ผลซ้ำได้

กฎธุรกิจทั้งหมดต้องอ่านเวลาจากนาฬิกากลางที่ฉีดค่าได้ และคำนวณใน Asia/Bangkok
ห้ามอ่านเวลาเครื่องตรง ๆ ในการตัดสิน OTP, QR, SLA, เลขรายปี, หมดเวลาแก้ไข
หรืออายุเอกสาร ต้องใช้ state transition ที่ตรวจสิทธิ์และเงื่อนไขก่อนเปลี่ยนข้อมูล
การรับเรื่อง การรับชำระ การออกเลขและบันทึก audit ที่เกี่ยวข้องต้องเป็น atomic
callback เดิมต้องไม่สร้างเลข ใบเสร็จ หรือคำขอซ้ำ
การ reset ต้องล้าง session ทุกคนและคืนข้อมูลทดสอบตามต้นฉบับ

### IV. สิทธิ์และข้อมูลส่วนบุคคลเป็นข้อกำหนดของทุกชั้น

ต้องตรวจ RBAC, เจ้าของคำขอ และขอบเขตแผนกที่หน้า API และการดาวน์โหลดไฟล์
ประชาชนเปิดคำขอคนอื่นต้องได้ 404 เหมือนเลขที่ไม่มีจริง
เลขบัตรและเบอร์มือถือต้องเข้ารหัสขณะเก็บตาม NFR-04; ชื่อ อีเมล และไฟล์แนบ
ยังเป็น Q-08 และต้องไม่มีเลขบัตรเต็มใน JSON ของเจ้าหน้าที่/หัวหน้า
ยกเว้นผลของคำสั่ง unmask ที่มีเหตุผลและบันทึก `UNMASK` ก่อนส่งข้อมูล
ผู้บริหารได้รับเฉพาะข้อมูลสรุป; หน้าตรวจเอกสารสาธารณะต้องปิดบังชื่อ
audit เป็น append-only; endpoint แก้/ลบต้องตอบ 405 ตามสัญญาแม้ admin เรียก
ต้องไม่เขียน secrets หรือข้อมูลส่วนบุคคลเต็มลง log และหลักฐานที่แชร์

### V. หลักฐานการทดสอบและขอบเขตตัวจำลอง

ระบบใช้หน่วยงานสมมติ ThaiD, PromptPay และลายเซ็น HMAC จำลองเท่านั้น
ห้ามเชื่อมบริการจริงหรืออ้างว่า HMAC นี้เป็นลายเซ็นที่รับรองทางกฎหมาย
ก่อนส่งมอบ implementation ต้องมีหลักฐาน baseline ครบ 51 TC และผลเปิด
BUG_MODE B01–B12 ทีละตัวตรงชุดที่ต้องล้ม/อาจล้มใน `BUGS.md`
ต้องแยก Playwright ออกจากการตรวจ encryption at rest แบบ inspection
ต้องไม่รายงานว่าผ่านโดยยังไม่ได้รันจริง; งานร่างเอกสารไม่เท่ากับเว็บที่พัฒนาเสร็จ

## Classroom Constraints

- ใช้ Next.js + SQLite + Playwright ตามตัวเลือกจาก session ต้นทาง
  รายละเอียด runtime และ package pin อยู่ในแผน ไม่เพิ่มบริการภายนอกที่โจทย์ไม่ต้องใช้
- `/api/test/*` เปิดเฉพาะเมื่อ `TEST_MODE=1`; เมื่อปิดต้องได้ 404
  BUG_MODE ใช้เพื่อพิสูจน์ test ในห้องเรียน และต้องแยกจาก baseline
- รองรับ body อย่างน้อย 6 MB, ไฟล์ 5,242,880 ไบต์ต้องผ่าน และ 5,242,881 ต้องได้
  400 พร้อมข้อความจากสัญญา ห้ามให้ framework ตัดเป็น 413 ก่อนตรวจ
- NFR ทุกข้อในโจทย์ต้องมีวิธีตรวจ; เป้าหมาย availability และขนาดการใช้งาน
  ต้องรายงานตามหลักฐาน ไม่อนุมานว่าผ่านจากการรันบนเครื่องเดียว

## Delivery Workflow and Quality Gates

1. Constitution → spec → research/plan/data model/contracts/quickstart → tasks
   แล้วตรวจ traceability ก่อนเริ่ม implementation
2. ทุก story ต้องมี acceptance scenario, งานที่มี path ชัดเจน และ TC ที่ตรวจได้
   งานที่เขียนไฟล์เดียวกันต้องเรียงลำดับ แม้จะอยู่คนละ story
3. ทบทวนข้อขัดแย้งกับ constitution ก่อนและหลังออกแบบ
   ถ้ามีข้อขัดแย้งต้องแก้แผน หรือเสนอ amendment ที่ระบุผลกระทบ ห้ามยกเว้นเงียบ ๆ
4. ก่อนส่งมอบเอกสาร ตรวจ placeholder, ลิงก์, รหัสข้อกำหนด/TC/บั๊ก, รูปแบบ tasks,
   dependency และความคงเดิมของเอกสารต้นฉบับ
5. ก่อนส่งมอบเว็บ ต้องรัน 51 TC, mutation matrix, inspection และ NFR checks
   เก็บผลจริงพร้อม environment, BUG_MODE และเวลาทดสอบ

## Governance

Constitution นี้กำกับงานออกแบบและพัฒนาชุดฝึกนี้ โดยไม่เปลี่ยนโจทย์ต้นฉบับ
การแก้ต้องระบุเหตุผล ข้อที่เปลี่ยน เอกสาร/TC ที่ได้รับผลกระทบ และหลักฐานทบทวน
ใช้ semantic versioning: MAJOR เมื่อเปลี่ยนหลักการจนงานเดิมไม่สอดคล้อง,
MINOR เมื่อเพิ่มหลักการ/ข้อบังคับ, PATCH เมื่อชี้แจงโดยไม่เปลี่ยนพฤติกรรม
ผู้ทบทวนทุกการส่งมอบต้องตรวจ Core Principles และ Quality Gates
คำถามถึงหน่วยงานต้องคงสถานะว่าเปิดอยู่จนมีคำตอบจริง; ไม่ใช้ความเห็นของ agent
แทนคำยืนยันจากหน่วยงาน การนำไปใช้จริงต้องผ่านการทบทวน security, capacity,
availability และการเชื่อมต่อจริงแยกจากชุดฝึกนี้
